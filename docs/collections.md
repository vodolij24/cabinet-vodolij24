## 1. Мета

Прозорий наскрізний контроль готівки: від вилучення з автомата до оприбуткування в касу.

Бізнес-цілі MVP:

1. **Поштучний облік** — кожна інкасація прив’язана до конкретного апарата, дати/часу і техніка. Відмова від обліку «кульками» без прив’язки до апарата.
2. **Автозакриття** — ≥ 95% інкасацій закриваються без ручного втручання звіряльника, якщо різниця факту й бази ≤ порогу (за замовчуванням 2%).
3. **Антифрод** — технік не тримає оборотні кошти компанії: видимий список «на руках», нагадування після 7 днів, підсвітка для керівника.
4. **Сліпий перерахунок** — касир вносить факт, не бачачи очікуваної суми з бази.

## 2. Глосарій

| Термін | Значення |
|--------|----------|
| **інкасація (пакет)** | Один факт вилучення готівки з одного автомата в конкретний момент. Одиниця обліку. Таблиця `collections`. |
| **очікувана сума / сума бази** | `total_sum` (або `sum_coins + sum_banknotes`) з Soliton / ручного введення. |
| **факт касира** | Сума, яку касир реально перерахував (`actualReceived` або окремо купюри + монети). |
| **здача** | Акт передачі набору інкасацій від техніка касиру. Зараз — `collection_handovers`; у MVP технік обирає конкретні пакети, а не лише кількість. |
| **на руках** | Інкасація створена і ще не передана касиру (накопичений робочий список техніка). |
| **історія інкасацій** | Усі проведені інкасації техніка, включно зі зданими й закритими. Без сум. Не робочий список здачі. |
| **журнал статусів** | Ланцюжок переходів: хто, коли, з якого статусу в який. Основа для метрик SLA. |
| **стрічка коментарів** | Спільні текстові записи по інкасації від техніка, касира і звіряльника. |
| **фантом** | Зайве/нульове спрацювання картки (подвійне притискання), яке не відповідає реальному пакету. |
| **дельта (Δ)** | Відносна різниця факту і бази, у %. Поріг за замовчуванням **2%** (конфігурується). |
| **звіряльник / фіндір** | Роль з повним доступом до сум і черги розбіжностей. У web — кабінет; phone-керівник — оперативні алерти. |

## 3. Як є зараз

Короткий gap, щоб не ламати вже зроблене.

| Тема | Зараз | Ціль MVP |
|------|--------|----------|
| Одиниця обліку | Рядок `collections` на апарат | Без зміни моделі: пакет = інкасація |
| Список техніка | `/{phone}` → **Інкасації**: нездані пакети без сум. Зріз з **01.09.2026** | Робочий список **на руках** (накопичується) + чекбокси здачі. Окремий згорнутий архів зданих/закритих. Канал MVP — phone UI; бот — лінк + нагадування |
| Коментарі | Лише в окремих сценаріях (ticket, note, фантом) | Єдина стрічка на кожну інкасацію: технік, касир, звіряльник |
| Журнал статусів | Немає історії переходів | Кожен перехід: актор, роль, timestamp; метрики «інкасація → закриття» — наступний етап по цьому логу |
| Здача | Касир створює здачу: технік + «заявлено / отримано пакетів»; система прив’язує **усі** нездані після попередньої здачі | Технік відмічає **конкретні** інкасації; касир приймає за списком апарат+адреса |
| Перерахунок касира | Касир бачить очікувану суму (монети/купюри/разом) і вводить факт або «Відсутній» | Касир **не** бачить очікувану суму; вводить факт купюр/монет; коментар; редагування щойно внесеного |
| Закриття | Усі пакети здачі з `recountStatus`, потім `recount_closed_at`. Алерти по **грн** (>200 / >1000), не по % | Авто **Закрита**, якщо Δ ≤ 2%; інакше **На розгляді** |
| Ручний пакет | Касир: «Додати пакет без даних апарата» | Технік додає вручну; касир може додати зайвий, якого не було в списку |
| Інциденти | Tickets після закриття здачі; missing → Telegram керівнику | Черга звіряльника + ручне закриття з причиною |
| Ролі сум | Технік уже не бачить сум у списку інкасацій | Закріпити: технік — лише статуси; касир — сліпий факт; звіряльник — усе |

Ключові файли: `lib/collection-handovers.ts`, `lib/collection-recount.ts`, `lib/technician-public.ts`, `lib/cashier-public.ts`, `app/(public)/[phone]/`, `app/(dashboard)/collections/`, `app/api/public/cashier/`, `app/api/public/technician/`.

## 4. Ролі та доступ до сум

| Роль | Канал | Обов’язки | Що бачить по сумах |
|------|--------|-----------|-------------------|
| **Технік** | Phone `/{phone}` (роль `technician`). Telegram: `/start` + deep-link на phone UI + нагадування. Повноцінний список у боті — не MVP | Фіксує/бачить **на руках**, галочками здає касиру, ручне додавання, фантом, коментар | **Не бачить** очікуваних і фактичних сум, **не бачить** Δ. Лише статус: на руках / передано / прийнято / закрито / на розгляді |
| **Касир** (Палич) | Phone `/{phone}` (роль `cashier`) | Приймає пакети за № апарата й адресою, вносить факт, відсутній / зайвий пакет, коментар | **Сліпо:** № апарата, адреса, дата. **Не бачить** суму бази. Бачить лише поля факту, які сам ввів |
| **Звіряльник / фіндір** | Web `/collections`, `/tickets` + phone керівника | Черга розбіжностей, ручне закриття, аналітика, антирейтинг | Повний доступ: база, факт, Δ грн і %, коментарі, тип збою |
| **Керівник (Олег)** | Phone + web | Антифрод 7 днів, аналітика техніків | Як звіряльник у частині підсвітки «гроші на руках > 7 днів» |

Правило UI: якщо роль не має права на суму — поле не рендериться і **не віддається** в public API (не лише `display: none`).

## 5. Життєвий цикл

Кожна інкасація (`collections.id`) проходить стани. Одна інкасація — в одній здачі.

```
Створена (на руках)
    → Передана касиру
        → Прийнята касиром
            → Закрита (авто)          Δ ≤ порогу
            → На розгляді             Δ > порогу | фантом | ручне введення | відсутній
                → Закрита (ручно)     звіряльник + причина
```

| Статус (UA) | Технічний сенс | Хто ставить |
|-------------|----------------|-------------|
| **Створена (на руках)** | Є рядок у `collections`, ще не в списку передачі касиру | Soliton / імпульс картки **або** технік вручну |
| **Передана касиру** | Технік відмітив пакет у списку здачі | Технік |
| **Прийнята касиром** | Касир підтвердив фізичну наявність | Касир |
| **Закрита (авто)** | Внесено факт, Δ ≤ 2% (конфіг) | Система |
| **На розгляді** | Δ > 2%, фантом, ручне додавання, відсутній пакет, немає даних апарата | Система / касир / технік |
| **Закрита (ручно)** | Звіряльник закрив після розслідування | Звіряльник / фіндір |

### Мапінг на поточну схему (міграція)

Зараз: `handoverId`, `recountStatus` (`done` \| `missing`), `actualReceived`, `no_device_data`, `collection_handovers.recount_closed_at`.

Потрібно додати явне поле статусу (рекомендовано `collections.status` + `closedAt` / `closedBy` / `closeReason` / `closeMode`: `auto` \| `manual`) і не ламати старі здачі: бекфіл з поточних прапорців.

Допустимий поріг Δ зберігати в конфігу (env або `settings`), не хардкодити 2% лише в UI.

Кожна зміна статусу пишеться в журнал (див. [§10](#10-коментарі-та-журнал-статусів)). Без рядка в журналі перехід не вважається збереженим.

## 6. Вимоги: технік

Канал MVP: public page техніка, вкладка **Інкасації**. Без сум. Telegram не дублює повний список у MVP — лише лінк на `/{phone}` і пуші (антифрод, здача прийнята).

Два шари списку:

| Шар | Що показує | Навіщо |
|-----|------------|--------|
| **На руках** (основний) | Усі проведені інкасації, які ще не здані касиру. Список **накопичується**, щойно з’явився рядок у Soliton / ручне додавання | Робочий перелік для здачі галочками |
| **Історія** (згорнутий архів) | Уже передані / прийняті / закриті, без сум | Відповідь на «всі проведені»; не для галочок здачі |

### BR-1.1 Баланс незданих

Онлайн-список **на руках**:

- № апарата, адреса, дата і час інкасації (Europe/Kyiv)
- кількість пакетів на апарат і загалом «на руках»
- лише свої автомати / свої `technicianId`
- оновлення: кнопка **Оновити** + poll, поки вкладка відкрита

**AC:** після появи рядка в `collections` (Soliton) список «на руках» показує його без перезапуску сервера, максимум з затримкою poll. Здані пакети зникають з основного списку і потрапляють в історію.

### BR-1.2 Передача касиру списком

Під час зустрічі з касиром технік відмічає **чекбоксами конкретні інкасації** (наприклад 25 із 25), не «кількість кульків».

- обрані → статус **Передана касиру**
- не обрані лишаються **На руках**
- касир далі працює лише з цим списком (апарат + адреса)

**AC:** неможливо здати «всі після попередньої здачі» без вибору рядків. Старий сценарій касира «заявлено N / отримано N» — замінити або лишити лише як контрольну звірку кількостей поверх вибраного списку.

### BR-1.3 Ручне додавання

Якщо апарат не віддав дані в Soliton: **Додати інкасацію вручну**.

Обов’язкові поля: автомат (зі списку закріплених або пошук за адресою), дата/час, коментар у **спільній стрічці** (причина). Суму технік **не** вводить у MVP (сума з’явиться з Soliton пізніше або її внесе касир як факт / звіряльник).

**AC:** ручний рядок одразу в «на руках»; тип збою = ручне введення → після факту касира за замовчуванням **На розгляді**, не автозакриття.

### BR-1.4 Фантом / збій картки

Подвійне притискання не має «висіти» на техніку. Технік позначає інкасацію **Фантомна / збій**, пише коментар у спільну стрічку і передає в загальному списку касиру.

**AC:** фантом не зникає з обліку; йде касиру як позначений; автозакриття вимкнене; потрапляє в чергу звіряльника.

### BR-1.5 Антифрод 7 днів

Якщо статус **Створена (на руках)** > 7 календарних днів:

- нагадування техніку (Telegram, якщо є `chat_id`)
- підсвітка в аналітиці керівника

**AC:** на 8-му календарному дні є і сповіщення, і позначка в панелі керівника. Відлік від `collections.date`.

## 7. Вимоги: касир

Канал: public page касира. Українською. Mobile-first.

### BR-2.1 Прийом за адресами

Список обов’язково містить **№ апарата** і **фізичну адресу**. Заборонено оперувати лише числом пакетів без розшифровки.

### BR-2.2 Заборона очікуваної суми

Прибрати з UI і з public API касира поля бази: `total_sum`, монети/купюри з Soliton, підказку «різниця».

Касир вводить:

- фактична сума купюрами
- фактична сума монетами  
  **або** один загальний факт (якщо купюри/монети не розділяють на місці)

**AC:** у відповіді `GET .../cashier/.../packages` немає сум бази. DevTools / джерело сторінки не містить очікуваної суми.

### BR-2.3 Розбіжності при прийомі

- **Не знайдено / відсутній** — технік позначив здачу, пакета немає
- **Додати пакет вручну** — технік привіз зайвий, якого не було в списку передачі (№ апарата + факт)

Відсутній → **На розгляді** (і подія для керівника, як зараз missing).

### BR-2.4 Коментар

Касир пише в **спільну стрічку коментарів** інкасації (розірваний кульок, немає маркування, чужий номер). Той самий тред бачать звіряльник і технік (технік — текст без сум).

### BR-2.5 Редагування щойно внесеного

Кнопка **Змінити** для факту, поки інкасація не в статусі **Закрита (ручно)** і поки звіряльник не взяв її в роботу. Захист від «0» замість «6».

Після зміни — перерахунок Δ і статус (авто / на розгляді) наново.

## 8. Автозвірка

### BR-3.1 Дельта

Після збереження факту:

\[
\Delta = \frac{\lvert \text{факт касира} - \text{сума бази} \rvert}{\text{сума бази}} \times 100\%
\]

- база = 0 і факт = 0 → окреме правило: не ділити на нуль; типово **На розгляді** (фантом / нуль), якщо не позначено інакше
- база = 0 і факт > 0 → **На розгляді**
- Δ ≤ порогу (default 2%) → **Закрита (авто)**
- Δ > порогу → **На розгляді**, черга звіряльника

Поріг — конфіг. Поточні пороги 200 / 1000 грн замінити або лишити як **додаткові** абсолютні алерти для звіряльника, не як правило автозакриття.

Ціль: **≥ 95%** інкасацій за період закриваються авто (вимірювати в звіті).

### BR-3.2 Часова прив’язка

Інкасація живе у своєму часовому зрізі (`collections.date`). Проміжне зняття (напр. 25-го) **не зливається** з повною інкасацією 29-го в один пакет і не повинно давати штучну Δ (кейс Віталіка / Олександра).

**AC:** дві інкасації одного апарата в різні дати — два рядки, дві здачі/факти, дві дельти.

Soliton на MVP: беремо те, що віддає API/вебхук, навіть якщо залізо барахлить. Компенсація — ручне додавання і фантоми.

## 9. Вимоги: звіряльник / фіндір

Web `/collections` (і за потреби окремий реєстр розбіжностей). Повний доступ до сум.

### BR-4.1 Черга на ручне закриття

Окремий список інкасацій **На розгляді** (не змішувати з таблицею всіх інкасацій кабінету). Це робоча черга звіряльника / фіндіра.

Фільтри:

- технік
- відхилення в грн і в %
- тип: фантом, ручне введення, розліт суми, відсутній, немає даних апарата

На картці черги обов’язкові: апарат, адреса, технік, Δ, **стрічка коментарів** і поле нового коментаря / причини закриття.

### BR-4.2 Ручне закриття

Після розслідування: **Закрита (ручно)** + обов’язкова причина (помилка купюроприймача, фальшива купюра, збій плати, підтверджений фантом, …).

Аудит: хто, коли, причина.

### BR-4.3 Аналітика MVP

- по техніках: % розбіжностей факт vs база
- по автоматах: хто частіше дає фантоми / некоректний розрахунок (для сервісу)

Антирейтинг «на руках > 7 днів» — на панелі керівника.

Існуючі звернення (`collection_tickets`) лишаються для довгого діалогу; не замінюють чергу статусів і не замінюють коротку стрічку коментарів на інкасації.

## 10. Коментарі та журнал статусів

### BR-5. Стрічка коментарів (усі ролі)

На **кожну** інкасацію — одна спільна стрічка. Пишуть:

| Хто | Коли обов’язково | Що можна |
|-----|------------------|----------|
| **Технік** | Ручне додавання, фантом | Будь-який робочий коментар по пакету на руках / в історії (без сум) |
| **Касир** | За потреби при прийомі / факті | Стан кулька, маркування, відсутність |
| **Звіряльник / фіндір** | При ручному закритті — обов’язково | Розслідування, причина закриття |

Правила:

- кожен запис: автор (ім’я, роль, id), текст, `createdAt`
- записи не видаляються (лише новий запис)
- технік і касир не бачать у стрічці сум і Δ; звіряльник бачить усе
- черга ручного закриття (BR-4.1) показує цю стрічку inline

### BR-6. Журнал статусів

Кожен перехід статусу — окремий рядок логу. Без логу перехід невалідний.

Поля рядка (мінімум):

- `collectionId`
- `fromStatus` / `toStatus`
- `actorRole`: `system` \| `technician` \| `cashier` \| `reconciler` \| `manager`
- `actorId`, `actorName`
- `createdAt` (timestamptz)
- опційно `payload` (handoverId, Δ, причина)

Обов’язкові події: створення (Soliton або технік вручну), передача касиру, прийом, факт, автозакриття, на розгляді, ручне закриття, зміна факту касиром.

**MVP:** писати лог і показувати звіряльнику на картці інкасації (хто створив, який технік, хто передав, хто прийняв, хто закрив).

**Наступний етап (не блокує MVP UI):** метрики по логу — час від `Створена` до `Закрита`, час на руках, час у черзі звіряльника.

### 11.1 Ядро (вже є)

| Таблиця | Роль |
|---------|------|

### 11.2 Очікувані доповнення MVP

- явний `status` інкасації + причина закриття
- стрічка коментарів (`collection_comments`: collectionId, authorRole, authorName, authorId, body, createdAt)
- журнал статусів (`collection_status_events`: collectionId, fromStatus, toStatus, actor*, createdAt)

- журнал антифрод-нагадувань

Гроші: `Decimal(10,2)`. Час: `timestamptz`, UI — Europe/Kyiv.

### 11.3 Soliton

Джерело створення інкасації (картка / імпульс). Кабінет не вигадує суму бази, якщо Soliton її віддав. Збої заліза → BR-1.3 / BR-1.4, без блокування MVP.

## 12. Архітектура

- Модульно, additive: не ламати `/machines`, задачі, ЗП, існуючі здачі без міграції.
- Public API за телефоном (як зараз). Суми — за роллю, на сервері.
- Кабінет Clerk (`assertApprovedAccess`) — звіряльник.
- Сповіщення: `sendStaffTextNotification` (Telegram `chat_id`).
- Ідемпотентність: одна інкасація не в двох відкритих здачах.

Екрани:

| Екран | Шлях |
|-------|------|
| Технік | `/{phone}` вкладка Інкасації |
| Касир | `/{phone}` здача + перерахунок |
| Керівник | `/{phone}` missing / no-device + антифрод |
| Звіряльник | `/collections`, `/tickets` |

## 13. Acceptance criteria

1. Технік у phone UI бачить накопичений список **на руках** (апарат, адреса, дата/час, статус; **без сум**) одразу після інкасації. Здані — в історії, не в робочому списку.
2. Здача = галочки на конкретних інкасаціях «на руках», не абстрактна кількість.
3. Касир бачить № + адресу; **не** бачить суму бази ні в UI, ні в API.
4. Після факту: Δ ≤ порогу → автозакриття; інакше окрема черга **На розгляді** для звіряльника.
5. Дві інкасації одного апарата в різні дні не змішуються.
6. Фантом і ручне введення не автозакриваються.
7. Відсутній пакет і зайвий пакет обробляються касиром.
8. Касир може виправити щойно введений факт до фінального ручного закриття.
9. На руках > 7 днів → нагадування техніку + підсвітка керівнику.
10. Звіряльник закриває вручну тільки з причиною в стрічці коментарів; дія є в журналі статусів.
11. На кожній інкасації є стрічка коментарів: писати можуть технік, касир, звіряльник.
12. Кожен перехід статусу пишеться в журнал (актор, роль, час). Звіряльник бачить історію на картці.
13. За контрольний період автозакриття ≥ 95% (якщо база Soliton якісна; фантоми/ручні не входять у знаменник авто або рахуються окремо — зафіксувати в decision log після першого місяця).
14. Немає спільної «звірки на вулиці»: технік передав список, касир перераховує постфактум.

## 15. Відкриті питання

1. Поріг 2% — від суми бази; що робити при базі 0?
2. Чи входить фантом у знаменник KPI 95%?
3. Чи вводить технік суму при ручному додаванні, чи лише касир/Soliton?
4. Чи лишаємо контроль «заявлено N / отримано N» як другу лінію після чекбоксів?
5. Чи показувати техніку статус **На розгляді** без сум (так, за BR)?
6. Редагування факту касиром — скільки часу / до якого статусу?
